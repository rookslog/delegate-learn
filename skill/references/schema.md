## Common envelope

Every record uses schema version `1` and contains:

- `event_type`: `route_planned`, `checkpoint`, `consultation`, `disposition`,
  `hypothesis`, or `policy_decision`;
- `project_id`: pseudonymous value from `project-id`;
- `run_id`: stable code shared by one delegated run;
- optional `consult_id` for advice;
- `event_id` and UTC `ts`, generated by the recorder when omitted.

All strings are bounded codes, not prose. Use lowercase hyphenated values where
possible. Lists contain at most 16 unique codes.

## Event types

### Short-form recording

`record-route` and `record-disposition` compute `schema_version`, `event_id`,
`ts`, and the pseudonymous `project_id`; the project path defaults to the
current directory and is never stored. `record-route` also defaults requested
role/model/effort to the planned values. `record-disposition` defaults friction
and confounder lists to empty and infers validator outcome only for `accept`,
`accept-after-revision`, and `revise`; other dispositions require an explicit
outcome. All other fields remain explicit semantic judgments or directly
observed metrics.

The original `record` command remains available for safe JSON via stdin or
`--file`, including checkpoint, consultation, hypothesis, and policy events.

### route_planned

Required fields: `task_class`, `closure_target`, `planned_role`,
`planned_model`, `planned_effort`, `requested_role`, `requested_model`,
`requested_effort`, `nearest_alternative`, `validation_oracle`, and
`falsifier_code`.

Optional fields include consequence, reversibility, ambiguity, write-scope
count, expected-advantage code, and packet-completeness code.

### checkpoint

Required fields: `checkpoint_code` and `checkpoint_outcome`. Use only for a
decision boundary, not each tool call.

### consultation

Required fields: `consult_id`, `advice_tier`, `advice_changed_action`,
`reproducible_counterexample`, and `root_disposition`.

### disposition

Required fields: `disposition`, `validator_outcome`, `rework_count`,
`friction_codes`, `confounder_codes`, and `observation_code`.

Directly observed `elapsed_seconds`, `input_tokens`, `output_tokens`, and
`total_tokens` are optional. Omit unavailable values.

### hypothesis

Required fields: `hypothesis_id`, `decision`, and `corroborating_run_count`.
This event records a candidate or narrowed hypothesis, not active policy.

### policy_decision

Required fields: `policy_id`, `decision`, `corroborating_run_count`, and
`rollback_code`. A human decision is required before activation.

## Codes and metrics

Initial friction codes include:

- `packet-too-broad`
- `unresolved-authority`
- `overlapping-write-scope`
- `missing-oracle`
- `silent-checkpoint`
- `scope-violation`
- `confirmation-biased-test`
- `advisor-no-new-evidence`
- `advisor-counterexample`
- `route-provenance-unknown`
- `tool-transport-failure`
- `external-auth-or-permission`
- `schema-drift`
- `validator-gap`

Use `unknown` for unavailable route provenance. Do not copy planned or requested
identity into observed fields.

## Interpretation rules

- Counts are descriptive and do not establish causality.
- Compare similar task classes and packet-completeness bands.
- Inspect project ledgers before interpreting a friction count.
- Record evidence against a hypothesis as well as evidence supporting it.
- Never rank a model universally from heterogeneous runs.
